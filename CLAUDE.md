# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Island Table": a private, self-hosted 2-6 player browser implementation of the 2025 edition of a classic island-trading board game and its 5-6 player (paired-player) expansion. Server-authoritative, dependency-free: Node.js 24+ built-ins only (`node:http`, `node:sqlite`, `node:crypto`, `node:test`), browser-native SVG/DOM on the client. There is no `npm install`, build step, bundler, linter, or TypeScript. Keep it dependency-free.

## Commands

```sh
npm start                         # node server.mjs  (http://localhost:3000)
npm run dev                       # node --watch server.mjs
npm test                          # node --test test/*.test.mjs
node --test test/engine.test.mjs  # one test file
node --test --test-name-pattern="paired" test/*.test.mjs   # tests matching a name
docker --context desktop-linux compose up -d --build       # Docker on this Windows machine (Linux containers), host port 8080
docker compose exec game node scripts/backup.mjs /data/backup.sqlite   # consistent live backup (refuses to overwrite)
```

Env vars: `PORT`, `HOST`, `DATA_DIR` (default `data/`, Docker `/data`), `PUBLIC_ORIGIN`, `BOT_PACE` (multiplies bot pauses, default 1; tests use 0.02–0.05), `BOT_AWAY` (ms offline before a bot stands in, default 60000). Compose also reads `BIND_ADDRESS` (default `127.0.0.1`) from `.env`.

`test/server.test.mjs` spawns `server.mjs` with `PORT=0` and a temp `DATA_DIR` under `tmp/`, detecting the port from the `http://localhost:<port>` line on stdout — keep that log line format. `tmp/` and `data/` are gitignored scratch/state.

Browser tests (`test/browser.test.mjs`) drive a real headless Chrome/Chromium/Edge through `test/browser.mjs`, a tiny DevTools Protocol client over Node's built-in `WebSocket` (no Playwright/Puppeteer). They auto-detect an installed browser (Edge on this machine), honor `BROWSER=<path>`, and skip when none exists. Each `newPage()` is an isolated browser context, i.e. a separate device with its own `localStorage`; clipboard writes are captured in `window.__copied`, and sound cues in `window.__sounds` once a test sets it to an array (see `listen`/`heard` in the browser tests; the cue names are the keys of `SFX` in `app.js`). The driver finds the endpoint via the profile's `DevToolsActivePort` file because Edge's launcher exits immediately and hands off to another process. Tests select elements by the client's `data-ui`/`data-command`/`data-vertex`/`data-edge`/`data-hex` attributes — keep those stable. To reach situations dice can't reliably produce (a seven with discards, specific hands, dealt dev cards, a stacked deck), the test-only `stage(server,pages,fn)` fixture opens the room's SQLite state between commands, lets `fn` edit it via `setHand`/`deal`/`topDeck` (which move cards to and from the bank and deck so supply and deck totals stay conserved), bumps `revision`, and reloads every page; everything after staging goes through the UI. Simultaneous actions (offers posted at once) can arrive in either order, so assert on content, not position. Buildings carry `data-owner` (-1 for neutral) and `data-kind`; trading happens in a panel floating over the board (`[data-ui="trade-panel"]` with tabs `data-mode="trade|bank"`, closed to `[data-ui="trade-launcher"]`; `trade-close`/`trade-show` dismiss and reopen offers); the lobby settings are selects `[data-setting="map|setup|goal|limit|friendly"]` for the host (others see `[data-value=…]`; `[data-ui="settings"]` carries the confirmed values as `data-map`, `data-goal`…); bots: the host adds one with `[data-command="addBot"]` on an open seat and removes it with `[data-remove-bot="<seat>"]`, bot lobby seats carry `data-bot`, an away human's sidebar card has `[data-takeover="<seat>"]`, and a seat a bot stands in for shows its name with " (Bot)" (`named()` in `app.js`); the starting roll is `[data-ui="order"]` with your dice as `[data-command="firstRoll"]` (`rollForStart(pages)` taps all at once and returns the pages that saw the result held); a finished round stays up 3 s with `data-held="tie|first"` (`heldOrder()` in `app.js`); discards happen in a window `[data-ui="discard"]` holding `#discard`, and holding more than the limit shows `[data-ui="discard-risk"]`; building happens from the build bar beside the hand (`[data-ui="build-bar"]`, buttons `data-mode="road|settlement|city"` and `data-command="buyCard"`); tooltips are `data-tip` attributes (never `title`), shown by one `#tip` layer after a hover with a moving pointer (a `pointerover` at the last `pointermove` position is ignored, so content appearing under a still pointer stays quiet) (the driver's `page.hover(selector)`) or a long press, and hovering a `.road[data-road][data-owner]` lights that player's longest route (`routeEdges` in `view()`, from `routePath()`); card pickers (trade, discard, invention) keep their counts in hidden `give-*`/`want-*`/`discard-*`/`take-*` inputs and the supply trade in hidden `give`/`want` inputs, so tests can still set them with `fill()`. `node scripts/review-screens.mjs <dir>` stages a 4-player game and saves screenshots of every major screen (via the driver's `screenshot()`), for design reviews. CI runners are much slower than this machine; set `THROTTLE=6` (CDP CPU throttling) to shake out timing flakes locally before pushing.

## Architecture

- **`lib/board.mjs`** — board graph (hexes, unique vertices and edges with adjacency), fixed presets for the 19-hex and 30-hex boards, ports, and number-token sequences (`BASE_NUMBERS`, `LARGE_NUMBERS`). Rule legality uses the graph, never screen coordinates.
- **`lib/engine.mjs`** — pure rules engine. `apply(state, playerIndex, cmd, random)` returns the next state for a command `{type: ...}` (`settings`, `start`, `ready`, `firstRoll`, `roll`, `road`, `settlement`, `city`, `buyCard`, `playCard`, `offer`/`acceptOffer`/`declineOffer`/`confirmOffer`/`cancelOffer`, `bank`, `discard`, `robber`, `steal`, `monopoly`, `invention`, `end`, `rematch`). Game flow is an explicit `phase` state machine (`lobby`, `order`, `setupSettlement`, `setupRoad`, `preRoll`, `discard`, `robber`, `steal`, `action`, `freeRoads`, `monopoly`, `invention`, `finished`). A room's `map` (`base`/`extended`, see `MAPS`) fixes the board, supply, deck and `seats` limit; `goal` (points to win), `limit` (discard when holding more) and `friendly` (friendly robber) are the other table settings. The host changes all of them in the lobby with `settings` (ranges in `LIMITS`); `POST /api/rooms` still accepts `map`/`setup` but the client sends only a name. After `start`, phase `order` has every player roll `firstRoll` (any order, ties reroll among the tied, `g.order`), then `place()` begins setup; `count` is 0 in the lobby and set to the number of players when the host starts (2+, all ready), so in-game rules such as paired turns (`count>4`) follow who actually plays. `upgrade()` gives pre-map saves their implied map when `server.mjs` loads them. All randomness comes through the injected `random(n)` so tests can be deterministic. `view(state, playerIndex)` produces the filtered per-player snapshot — opponents' cards, hidden VP totals, and deck order must never leak through it. Only the current player starts trade offers; others accept (willingness, stored in `offer.accepted`), decline, or counter (`offer` with `counterTo`), and the current player completes one with `confirmOffer` (or by accepting a counter). History is `g.events`: structured entries `{id,turn,kind,p,...}` written by `log(g,kind,data,secret)`; `secret` (`{to:[players],...}`, e.g. a stolen resource or a bought card) is stripped by `view()` for everyone else. The client's `story()` in `app.js` renders them; old saves' `{turn,text}` entries still render as text. Roll events carry per-hex `gains` for animations.
- **`lib/bot.mjs`** — `decide(view,random,{offerAge})` returns one command (or `{wait:ms}` while its own offer awaits answers) from **only** `view(g,p)` of its seat; `fallback(view)` is the plainest legal move. Per-turn limits (one player offer, a few supply trades, 30 moves) are counted from `v.events`, so it stays pure. Strength is "average": it plans one build ahead and picks among the top few options. Tune with `node scripts/bot-stats.mjs`. Engine side: `addBot`/`removeBot` (host, lobby; `bot:true`, always ready, names from `BOT_NAMES` + " (Bot)"), `takeover {player}` (sets `auto`; `auto:true` in the command = the server's automatic one, never accepted from HTTP), `release`, and `pending(g)` (who owes a decision now).
- **`server.mjs`** — HTTP API + SSE live updates (not WebSockets) + SQLite persistence. Routes: `/health`, `POST /api/rooms`, `/api/rooms/:id/{join,events,commands}`. Whole game state is stored as JSON in `rooms`; `sessions` stores SHA-256 hashes of bearer seat tokens; `commands` stores `(room, player, id)` for idempotency. Each command carries an ID and expected revision: stale revisions are rejected, duplicate IDs are acknowledged without re-applying, and state is committed in a `BEGIN IMMEDIATE` transaction before acknowledging, then broadcast as `view()` to each connected client. Bots run in the server: after every commit `wake(room)` sets one timer if a bot or `auto` seat is in `pending()`; `step()` asks each such seat inside a transaction and applies the first real move (bot offers get an `offerId` from `randomBytes`). A 5 s presence check takes over (`auto`) for a human the game waits on who has been offline `BOT_AWAY` ms while another human is connected; a stream connect or any command from an `auto` seat releases it first in its own commit. Rooms with bots are woken at startup.
- **`public/`** — single-page client (`app.js`, `index.html`, `style.css`); renders the board as original SVG. Resource icons are original art in an SVG sprite inlined in `index.html` (`#ico-wood` … `#ico-desert`, referenced with `<use>` and the `icon()` helper); edit `scripts/icons.mjs` and run `node scripts/icons.mjs` to regenerate it rather than hand-editing the sprite. The same sprite holds interface icons (`#ui-arrow`, `#ui-close`, `#ui-check`, `#ui-sound-on` …, used via the `ui()` helper): Font Awesome Free path data kept in `UI` in `scripts/icons.mjs`, CC BY 4.0, credited in the README and How to play. The client also stores seat tokens in `localStorage` key `island-seats` (`{room:{room,token,at,over?}}`); on the home page `checkSeats()` drops seats whose room is gone or token is rejected (401/404), `prune()` drops games finished more than 7 days ago and keeps the 20 most recently used.
- **Tests** — `engine.test.mjs` (rules, edge cases), `bot.test.mjs` (bot games at 2-6, leak test, trade answers, strength bounds) on the shared `test/sim.mjs` (`rng`, the `scripted` player, `bot`, `play()` with a simulated clock, `setHand`), `matches.test.mjs` (complete seeded games at 2-6 players using only real commands, with JSON round-trips simulating save/restore), `server.test.mjs` (auth, idempotency, private views, stale revisions, restart persistence), `browser.test.mjs` (invite → lobby → simultaneous ready → setup → turns → reload → seat recovery across devices; phone-width layout).
- **Stale revisions in the client** — a 409 refreshes state and shows "try again", keeping form values (`render(true)`). `retryContext()` in `app.js` lists the commands `command()` retries automatically instead: lobby `ready` (friends ready up simultaneously), lobby `settings`, `firstRoll` during `order` and `offer`/`acceptOffer`/`declineOffer` during `action` (several players answer or counter at once). A retry happens only if the context it returns (own ready flag; turn/active/role) is unchanged after the refresh. It also retries every command of the active player during their own `action` phase (others can only answer offers then) and `discard` while the owed count is unchanged, because bots move alongside people. Add new auto-retried commands there. `command()` drops a repeat of the in-flight command type (double clicks) but queues a different one, because the SSE stream often reveals the next choice (Monopoly, Invention) before the HTTP response returns; it also skips redrawing when the stream already delivered the response's revision.

## Code style

Code is written in a compact, dense style: long single-line functions, minimal whitespace, terse names, ES modules (`.mjs`). Match it when editing rather than reformatting.

## Rules and conventions

- `RULES.md` is the rule-to-source mapping and the list of **explicit digital conventions** for underspecified cases (Longest Route traversal, Road Building with < 2 legal spots, two-desert robber start, dev-card aging per personal action opportunity in paired turns, neutral blockers in fixed 5-player setup, etc.). Update it when changing any such behavior. The saved rules identifier is `2025-v1`.
- Rule source of truth is the 2025 rulebooks; text extracts live in `tmp/pdfs/*.pdf.txt`. Do not bundle the PDFs or their artwork in the app.
- No older-edition rules: no special building phase; Player 2 in paired turns never trades with players and never rolls.
- Moves are made only by players, by bot seats the host added, and by a bot standing in for an offline player (handed over by someone at the table, or after 60 s offline while the game waits on them and another human is connected; released the moment they return). No auto-skips or forfeits. Bots decide only from `view()` of their own seat.
- Schema is additive and auto-created at startup; incompatible changes need an explicit migration.
- `PLAN.md` is the original proposal; its React/TypeScript/Socket.IO stack was deliberately not used.
- Work tracking: every piece of feedback or planned work is a work item in `docs/work/` (index `docs/work/README.md`, one file per item with feedback, decisions, plan, review, progress and handoff prompt). Handle owner feedback and continue open items with the `answering-feedback` skill (`.claude/skills/answering-feedback/SKILL.md`): question until nothing is open, plan, agent review (up to 3 rounds), then implement one commit per step. Check the index at the start of a session.
